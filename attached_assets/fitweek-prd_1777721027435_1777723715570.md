# FitWeek — Product Requirements Document

---

## Problem Statement

Every morning, users face a recurring time cost: standing in front of their wardrobe, mentally assembling an outfit, only to discover that the item they had in mind is in the laundry pile. This forces an unplanned re-decision under time pressure, contributes to being late, and creates low-grade daily stress. No existing app solves all three dimensions of the problem simultaneously: knowing what clothes are *actually available* (not in laundry), planning *ahead* for the full week, and accounting for the *weather* each day.

---

## Solution

FitWeek is a mobile-first AI wardrobe planner that lets users photograph their clothes once, then swipe through a filtered, weather-aware deck on Sunday evening to lock in outfits for the entire week. The app only surfaces garments that are clean and not already scheduled, and suppresses weather-inappropriate layers based on a 7-day forecast. A laundry basket system ensures dirty clothes are never suggested. A virtual try-on preview — powered by the IDM-VTON model hosted on Hugging Face Spaces via the Gradio client — lets users see confirmed outfits on their own photo before committing. The weekly plan is exportable to a calendar and shareable as an outfit card.

## User Stories

### Authentication

1. As a new user, I want to sign in with my Google account, so that I can start using the app without creating a separate account.

### Onboarding & closet setup

2. As a new user, I want to take a full-body photo of myself during setup, so the app can generate virtual try-on previews using my actual appearance.
3. As a new user, I want to photograph individual garments with my phone camera, so that I can digitise my wardrobe without manual data entry.
4. As a new user, I want the app to automatically classify each garment by category (t-shirt, trousers, jacket, dress, etc.) and dominant colour, so that I don't have to tag items manually.
5. As a new user, I want to review and correct any misclassification after upload, so that the app's suggestions are accurate from day one.
6. As a user, I want to add garments incrementally over time, so that I don't need to photograph my entire wardrobe before the app is useful.
7. As a user, I want to see all my garments in a browsable grid view grouped by category, so that I can get an overview of my full wardrobe.
8. As a user, I want to edit a garment's category or colour after it has been added, so that I can correct mistakes I notice later.
9. As a user, I want to remove a garment I no longer own, so that it stops appearing in my wardrobe.
10. As a user, I want to retake my model photo from settings, so that I can update it if my appearance changes.

### Garment status & laundry

11. As a user, I want to long-press any garment card to change its status (clean, worn, laundry) or edit its details, so that I can keep the app in sync with my physical wardrobe from a single interaction.
12. As a user, I want worn and laundry items to be automatically hidden from outfit suggestions, so that the swipe deck only shows me what I can actually wear.
13. As a user, I want a dedicated Laundry Basket tab that lists all items currently in the laundry, so that I can see what's unavailable at a glance.
14. As a user, I want to mark items in the laundry basket as washed (returning them to clean status), so that freshly laundered clothes reappear in suggestions.
15. As a user, I want the option to "skip for the rest of this week" during swiping, so that items I recently wore but that are technically clean don't keep appearing.
16. As a user, I want items I skipped during a same-day planning restart to reappear automatically, so that I can reconsider them without resetting the whole session.
17. As a user, I want to mark a garment as worn manually by tapping a button on a confirmed outfit, so that its status is updated when I actually wear it.
18. As a user, I want a visual indicator on garment cards showing their current status, so that I can see at a glance which items are clean, worn, or in the wash.

### Weather-aware suggestions

19. As a user, I want the app to fetch a 7-day weather forecast for my location automatically, so that my weekly outfit suggestions are contextually appropriate.
20. As a user, if I decline location access, I want to manually enter my city so that weather filtering still works.
21. As a user, I want to change my saved location from settings, so that the forecast stays accurate if I travel.
22. As a user, I want weather-inappropriate garment categories to be suppressed per day (e.g. no sandals on a rainy day, no heavy coats on a 30°C day), so that I'm never suggested something unsuitable.
23. As a user, I want to see a weather summary badge (temperature + condition icon) on each day in the weekly calendar view, so that I understand why certain items were filtered out.
24. As a user, I want to override the weather filter for a specific day, so that I can still select an item the app has suppressed if I choose to.
25. As a user, I want the weather data to refresh each time I open the app, so that sudden forecast changes are reflected in my suggestions.

### Weekly planning & swipe UX

26. As a user, I want to open a weekly planner view (Mon–Sun) and select a day to start planning, so that I can build outfits for multiple days in one session.
27. As a user, I want to see a swipeable card deck of clean, weather-appropriate garments for a selected day, so that outfit selection feels fast and intuitive.
28. As a user, I want to swipe right to add a garment to the current day's outfit and swipe left to skip it, so that building an outfit requires minimal cognitive effort.
29. As a user, I want haptic feedback on each swipe action, so that the interaction feels native and satisfying.
30. As a user, I want to see the outfit I'm building assemble visually as I swipe right, so that I can see how pieces combine in real time.
31. As a user, I want to be notified when my swipe deck is running low, with skipped items reintroduced automatically, so that I never hit an empty deck mid-session.
32. As a user, I want to confirm or discard the outfit I've assembled for a day, so that I control what gets locked into the calendar.
33. As a user, I want confirmed outfits to remove their component garments from suggestions for other days that same week, so that I don't accidentally plan the same item twice.
34. As a user, I want to edit a confirmed outfit after the fact, so that I can make changes if my plans shift.
35. As a user, I want to clear an entire day's outfit and start over, so that I'm not locked in to an early decision.
36. As a user, I want to rename a confirmed outfit, so that I can give it a label that's meaningful to me.

### Reminders

37. As a user, I want to receive a Sunday evening notification reminding me to plan my week's outfits, so that I build the habit without having to remember manually.

### Virtual try-on (VTO)

38. As a user, I want to generate a virtual try-on image of a confirmed outfit, so that I can see how the pieces look together before the day arrives.
39. As a user, I want the VTO to be generated via a single tap after confirming an outfit, so that accessing this feature requires no technical knowledge.
40. As a user, I want the VTO image to be saved alongside the outfit in my weekly calendar, so that I can reference it each morning.

### Calendar export & sharing

41. As a user, I want to export my full week's outfit plan as an iCal (.ics) file, so that I can add it to my Google Calendar or Apple Calendar.
42. As a user, I want each calendar event to include the outfit name, garment list, and weather forecast for that day, so that the export is genuinely useful.
43. As a user, I want to generate a shareable outfit card image (outfit photo + day + weather summary) for any confirmed outfit, so that I can post it to social media.

## Implementation Decisions

### Modules

**Auth module**
Handles sign-in via Supabase Auth with Google OAuth as the primary provider. On first sign-in, creates a row in the `users` table seeded with the Supabase `auth.users` id. Manages session tokens and exposes the current user context to all other modules. Onboarding flow (model photo capture + first garment upload) is gated behind a completed auth session.

**Garment ingestion module**
Accepts an image from the device camera or photo library, uploads it to Supabase Storage in a user-scoped bucket (`/garments/{user_id}/{garment_id}`), sends the public URL to the Roboflow fashion classification API, and receives category + colour + confidence metadata. If `confidence ≥ 0.70`, the classification is applied silently but remains editable. If `confidence < 0.70`, or if the returned category is unrecognised, the garment is saved with `category = 'uncategorized'` and the correction UI is shown automatically. Writes a garment record to the database and returns a structured garment object. Stateless and independently testable.

**Garment status module**
Manages the `status` field (`clean`, `worn`, `laundry`) and the `last_skipped_at` / `skip_until` fields on garment records. Exposes the following methods:
- `markWorn` — sets `status = 'worn'`. Triggered by explicit user action only; there is no automated end-of-day transition.
- `sendToLaundry` — sets `status = 'laundry'`.
- `markWashed` — sets `status = 'clean'`, clears `skip_until`.
- `skipForSession` — sets `last_skipped_at` to now. The suggestion filter excludes this garment for the remainder of the current calendar date. Resets automatically the next calendar day.
- `skipForWeek` — sets `skip_until` to the ISO date of the following Monday. The suggestion filter excludes this garment until that date has passed.

These two skip types are independent. `skipForSession` and `skipForWeek` do not interact. All status transitions write to Supabase; no local-only state.

**Weather service module**
On app open, attempts to fetch the 7-day forecast from the OpenWeatherMap API using the device's GPS location. If location permission is denied, falls back to a `fallback_city` string stored on the user record. If the API call fails, reads a cached forecast from AsyncStorage (valid for up to 24 hours) and shows a "Using cached forecast" banner. If no cache exists, disables weather filtering and shows all garment categories with a warning banner in the swipe deck. On a successful fetch, persists the forecast to AsyncStorage. Exposes a `getSuggestableCategories(date)` method that returns the set of garment categories appropriate for that day's conditions. Cached in-session to avoid redundant API calls.

**Suggestion filter engine**
Given a `userId` and a target `date`, queries the garments table with the following conditions:
- `status = 'clean'`
- `deleted_at IS NULL`
- `last_skipped_at` is null or its calendar date differs from today
- `skip_until` is null or is a past date
- `id NOT IN` (garment IDs already scheduled for this week in confirmed or draft slots)
- `category IN` (categories returned by the weather service for that date)

Returns garments ordered by: (1) category variety — tops, bottoms, and outerwear are interleaved to prevent monotonous runs — then (2) `created_at` descending, so newer additions surface first.

**Weekly schedule module**
Manages `OutfitSlot` records (user, date, garment IDs, name, status: `draft` | `confirmed` | `archived`). Exposes methods: `addGarmentToSlot`, `removeGarmentFromSlot`, `confirmSlot`, `clearSlot`, `renameSlot`. Garments move to `worn` status only via explicit user action (`markWorn` or "Mark all as worn" on a confirmed slot) — there is no automated end-of-day transition. Draft slots that are not confirmed within 24 hours of creation are automatically discarded on the next app open; garments referenced by discarded drafts return to the eligible suggestion pool. On the first app open of a new ISO week (after midnight Sunday), confirmed slots from the prior week are moved to `archived` status; draft slots from the prior week are discarded.

**VTO module**
Accepts the outfit's garment list and the user's `model_image_url`. Selects the single hero garment using the following category priority order: `dress` → `top / shirt` → `jacket / outerwear` → `trousers / skirt`. Calls the IDM-VTON Hugging Face Space (`yisol/IDM-VTON`) via the `@gradio/client` npm package using the `/tryon` endpoint. Both the human image and garment image are fetched as blobs before the call. The human image is passed in ImageEditor format (`{ background: humanBlob, layers: [], composite: null }`); the garment image is passed as a plain blob. Auto-masking and auto-crop are both enabled (`true`) so no manual mask is required. Denoising steps are set to `30` for demo-quality output; seed is randomised per call. Returns the generated image from `result.data` and saves the URL to `vto_image_url` on the relevant `OutfitSlot` record. The Space is free but rate-limited; the module should surface a clear loading state and a graceful error message if the Space is cold or the request is throttled. Multi-garment compositing is out of scope for v1.

**Calendar export module**
Accepts the full week's confirmed `OutfitSlot` records and generates a valid iCal `.ics` string. Each event uses the slot's `name` field (auto-generated from garment list if the user has not set a custom name), garment list, and weather summary. Triggered by a single export button in the weekly view.

**Share card module**
Composes a shareable image card from the outfit preview image, the day label, and the weather badge. If `vto_image_url` is populated, uses the VTO image. If not, falls back to a 2×2 grid collage of the component garment flat-lay images. Uses React Native's `Share` API to open the native share sheet.

### Schema

```
users
  id uuid PK  -- matches auth.users id
  model_image_url text nullable
  fallback_city text nullable
  created_at timestamptz

garments
  id uuid PK
  user_id uuid FK → users.id
  category text
  color text
  image_url text
  status text  -- 'clean' | 'worn' | 'laundry'
  last_skipped_at timestamptz nullable
  skip_until date nullable
  deleted_at timestamptz nullable
  created_at timestamptz

outfit_slots
  id uuid PK
  user_id uuid FK → users.id
  scheduled_date date
  garment_ids uuid[]
  name text nullable  -- auto-generated on confirm if null; user-editable
  status text  -- 'draft' | 'confirmed' | 'archived'
  vto_image_url text nullable
  created_at timestamptz
```

### API contracts

- **Supabase Auth**: Google OAuth via `supabase.auth.signInWithOAuth({ provider: 'google' })`
- **Roboflow**: POST image → `{ category, color, confidence }`
- **OpenWeatherMap**: GET `/forecast?lat&lon&appid` → 7-day daily forecast
- **HuggingFace IDM-VTON** (`yisol/IDM-VTON` via `@gradio/client`): `app.predict("/tryon", [{ background: humanBlob, layers: [], composite: null }, garmentBlob, description, true, true, 30, seed])` → `result.data` containing the generated image

### Key architectural decisions

- All persistent state lives in Supabase. No local-only state for garments or schedule.
- Garment images and user model photos are stored in Supabase Storage in user-scoped buckets with Row-Level Security. Only the owning user can read or write their own images. Images are fetched as blobs by the VTO module before being sent to the Hugging Face Space; the Space does not need to access Supabase URLs directly.
- Authentication uses Supabase Auth (Google OAuth). The `user_id` FK on all tables is seeded from `auth.users.id`. Row-Level Security policies on all tables restrict reads and writes to the owning user.
- Garment deletion is soft: setting `deleted_at` excludes the record from all queries. Orphaned `garment_ids` in `outfit_slots` that reference soft-deleted garments are skipped silently in calendar export, VTO, and share card modules.
- Weather filtering rules are encoded as a static lookup object (category → min/max temp + conditions), not AI inference. This makes the filter fast, deterministic, and easy to demo.
- Skip semantics are clearly separated: `skipForSession` is calendar-date-scoped; `skipForWeek` sets an explicit `skip_until` date. They are independent and do not interact.
- Worn status transitions are manual only. There is no automated end-of-day trigger; mobile background scheduling for this is unreliable and adds complexity not warranted for v1.
- The suggestion filter runs as a Supabase query, not client-side filtering, to keep the deck size predictable and avoid loading unnecessary garment data.
- VTO uses the IDM-VTON Hugging Face Space (`yisol/IDM-VTON`) via `@gradio/client`. It is free but rate-limited. The Space can have cold start latency of 30–60 seconds after periods of inactivity; the UI must show a visible loading state for the duration. Only the hero garment is sent per generation; multi-garment compositing is deferred to v2.
- The app plans for the current ISO week (Mon–Sun) only. Planning future weeks is out of scope for v1.
- The weekly reminder notification is scheduled locally on device via Expo Notifications for Sunday at 7pm in the user's local timezone. No backend push infrastructure is required.

## Testing Decisions

**What makes a good test here:** Test the external behaviour of each module through its public interface only. Do not test internal query structure or API call mechanics. Tests should answer: "given this input state, does the module return the correct output?" Tests should be runnable without network access using mocked API responses.

**Modules to test:**

- **Suggestion filter engine** — highest priority. Given a set of garment records with various statuses, a set of already-scheduled garment IDs, and a mocked weather category set, assert that the returned deck contains exactly the correct garments and is in the correct interleaved category order. Cover edge cases: all garments in laundry (empty deck), all garments already scheduled, `skip_until` in the future vs past, soft-deleted garments excluded.
- **Garment status module** — test each status transition method. Assert that `sendToLaundry` correctly sets status and that `markWashed` returns it to clean. Assert that `skipForWeek` sets `skip_until` to the following Monday. Assert that `skipForSession` sets `last_skipped_at` to today's date and that the garment reappears in the filter the following calendar day.
- **Garment ingestion module** — given a mocked Roboflow response with confidence above and below 0.70, assert that the correction UI flag is set correctly. Assert that a failed API call saves the garment with `category = 'uncategorized'` and sets the correction UI flag. Assert that an unrecognised category also triggers the correction UI.
- **Weather service module** — given a mocked OpenWeatherMap response, assert that `getSuggestableCategories` returns the correct category set for a hot sunny day vs a cold rainy day. Assert that a failed API call with a valid cache returns the cached data. Assert that a failed API call with no cache returns all categories.
- **Weekly schedule module** — assert that confirming a slot removes component garments from subsequent days' suggestion pools. Assert that clearing a slot restores garments to the filter-eligible pool. Assert that a draft slot older than 24 hours is discarded on next check.
- **VTO module** — given a list of garments of mixed categories, assert that the hero garment selector returns the correct item (dress over top over jacket over trousers). Assert that when `vto_image_url` is saved, it is written to the correct `OutfitSlot` record.
- **Calendar export module** — given a set of confirmed `OutfitSlot` records with and without a custom `name`, assert that auto-generated names are produced correctly, and that the output `.ics` string contains all required event fields and is valid iCal syntax.

## Out of Scope

- Custom avatar creation or 3D mesh rigging (replaced by IDM-VTON 2D try-on via Hugging Face Spaces)
- Multi-garment VTO compositing (v1 sends hero garment only; deferred to v2)
- Real-time cloth physics or AR try-on via MediaPipe/ARKit
- Custom CNN training for garment classification (Roboflow handles this)
- Social features (following other users, public wardrobes)
- E-commerce integrations or purchase suggestions
- Multi-user / household wardrobe sharing
- Paid subscription tiers or monetisation logic
- Android-specific native features beyond standard React Native Expo support
- Outfit history analytics (cost-per-wear, frequency tracking)
- Planning for future weeks beyond the current ISO week

## Further Notes

**Hackathon submission context:** This PRD targets the Replit Agent 4 Buildathon (24-hour window). Build priority order is: (1) auth + garment ingestion + status, (2) suggestion filter engine, (3) swipe deck UI with haptics, (4) weather filter, (5) weekly calendar view, (6) IDM-VTON VTO via Hugging Face Spaces, (7) calendar export + share card.

**Demo video script anchor:** The submission video should open with the problem (morning wardrobe indecision, finding the chosen shirt is dirty), demonstrate Sunday evening planning in under 90 seconds, show the laundry basket feature explicitly, and close with VTO preview and calendar export.

**Pitch one-liner:** "Tinder for your wardrobe — only shows you what's actually clean and appropriate for the weather."

**Competitive differentiator:** No existing consumer wardrobe app (Whering, Acloset, Fits, Smart Closet) combines laundry-aware filtering, weather suppression, and a weekly planner in a single swipe-based flow. The laundry basket is the feature competitors have explicitly not built.
